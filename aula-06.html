Visão geral da técnica

Onde essa abordagem se encaixa na IA?

Estamos estudando uma abordagem da IA simbólica. Nela, o conhecimento é representado explicitamente por símbolos, relações e regras que o sistema consegue manipular.

Componentes

Duas partes trabalham juntas

Representação: transforma uma situação do mundo real em fatos, relações e regras.

Inferência: usa essa representação para aplicar regras e produzir novas conclusões.

Representação

Como transformar conhecimento em algo que o sistema consiga usar?

Um programa não entende uma situação como nós. Primeiro precisamos transformar o que sabemos sobre o problema em elementos explícitos que ele consiga armazenar e relacionar.

Situação do mundo real

Uma API de vendas começou a falhar

Durante a investigação, a equipe observa que a API retorna erro 500, o banco de dados está indisponível e o servidor ainda possui espaço em disco. A equipe também sabe que a API depende do banco e executa no servidor_01.

Existem duas causas comuns que queremos representar: uma falha associada ao banco de dados ou uma falha associada ao disco do servidor.

FATOS
api_retorna_500
banco_indisponivel
servidor_tem_espaco

RELAÇÕES
depende_de(api, banco)
executa_em(api, servidor_01)

REGRAS
R1: SE api_retorna_500 E banco_indisponivel
    ENTÃO falha_associada_ao_banco

R2: SE api_retorna_500 E disco_cheio
    ENTÃO falha_associada_ao_disco

R3: SE falha_associada_ao_banco
    ENTÃO verificar_conexao_banco

Essa modelagem será nossa referência para entender os três componentes abaixo.

Fato

O que sabemos?

Descreve o caso: informações observadas durante o incidente.

api_retorna_500
banco_indisponivel
servidor_tem_espaco

Relação

Como as coisas se conectam?

Organiza os elementos do domínio: registra dependências e vínculos conhecidos.

depende_de(api, banco)
executa_em(api, servidor_01)

Regra

O que pode ser concluído?

Diz o que pode ser concluído quando certas condições são satisfeitas.

R1: erro_500 + banco_indisponivel
    → falha_associada_ao_banco

R2: erro_500 + disco_cheio
    → falha_associada_ao_disco
Nesta etapa, estamos apenas representando. A base contém mais de uma possibilidade. Descobrir quais regras realmente podem ser aplicadas aos fatos disponíveis é tarefa da inferência.

Inferência

Como o sistema produz uma conclusão?

O mecanismo de inferência verifica quais regras podem ser aplicadas aos fatos disponíveis. Cada conclusão produzida pode se tornar um novo fato e ativar outra regra.

Encadeamento para frente

Começamos com aquilo que sabemos e verificamos, uma a uma, quais regras têm todas as suas condições satisfeitas.

Fatos iniciais:
api_retorna_500
banco_indisponivel
servidor_tem_espaco

R1: SE api_retorna_500 E banco_indisponivel
    ENTÃO falha_associada_ao_banco

R2: SE api_retorna_500 E disco_cheio
    ENTÃO falha_associada_ao_disco

R3: SE falha_associada_ao_banco
    ENTÃO verificar_conexao_banco
api_retorna_500 + banco_indisponivel→R1 pode ser aplicada e produz falha_associada_ao_banco.
api_retorna_500 + disco_cheio→R2 não pode ser aplicada: disco_cheio não é um fato conhecido.
falha_associada_ao_banco→R3 passa a ser aplicável e produz verificar_conexao_banco.
Observe: ter uma regra na base não significa que ela será usada. R2 representa uma possibilidade válida, mas não dispara neste caso porque uma de suas condições não está presente.

Só para reconhecer

E o encadeamento para trás?

Existe uma estratégia que começa pela hipótese que queremos verificar. Em vez de perguntar “o que posso concluir?”, perguntamos “o que preciso provar para sustentar esta conclusão?”.

EstratégiaComeça porPergunta
Para frenteFatos disponíveisO que posso concluir?
Para trásHipótese ou objetivoO que preciso provar?

Nesta aula, nosso foco será o encadeamento para frente.

Prática guiada

Projete um sistema de diagnóstico de incidentes

Sistemas baseados em conhecimento combinam bem com tarefas de diagnóstico: observações viram fatos, conhecimento técnico vira regra e a inferência ajuda a levantar hipóteses ou indicar a próxima verificação.

Cenário

Uma plataforma de vendas apresenta falhas intermitentes

Usuários relatam erros 500 e respostas muito lentas. Durante a investigação, a equipe coleta:

  • a API retorna erro 500;
  • a latência da API está alta;
  • o banco de dados está acessível;
  • o número de conexões abertas com o banco está no limite;
  • o cache está indisponível;
  • o servidor possui espaço em disco.

A arquitetura também informa que a API depende do banco de dados e utiliza um serviço de cache.

Objetivo do sistema: a partir das observações do incidente, indicar quais problemas podem estar associados à falha e quais verificações devem ser realizadas em seguida.

1. Modele os fatos

Transforme as observações relevantes em fatos simples. Um exemplo já está resolvido:

"A API retorna erro 500"
        ↓
api_retorna_500

Agora modele as demais observações. Procure usar nomes curtos, consistentes e sem incluir conclusões antecipadas.

2. Modele as relações do domínio

Nem toda informação é um fato do incidente. Algumas descrevem como os componentes do sistema se relacionam.

"A API depende do banco"
        ↓
depende_de(api, banco)

Represente também a relação entre a API e o cache.

3. Transforme conhecimento técnico em regras

A equipe fornece o conhecimento abaixo em linguagem natural. Converta cada item para o formato SE ... ENTÃO ....

  1. Se a API retorna erro 500 e o banco está indisponível, investigar falha de acesso ao banco.
  2. Se a latência da API está alta e o número de conexões com o banco está no limite, investigar saturação do pool de conexões.
  3. Se a API apresenta falha e o cache está indisponível, investigar o serviço de cache.
  4. Se a API apresenta falha e o disco está cheio, investigar armazenamento.

Uma regra pode produzir uma hipótese intermediária; outra regra pode usar essa hipótese para recomendar uma ação de verificação.

4. Execute a inferência manualmente

Com os fatos do cenário e as regras que você modelou:

  1. liste os fatos inicialmente conhecidos;
  2. marque quais regras têm todas as condições satisfeitas;
  3. adicione as conclusões produzidas aos fatos conhecidos;
  4. repita o processo enquanto surgirem novas conclusões;
  5. registre também as regras que ficaram bloqueadas e qual condição estava faltando.

Ao final, represente pelo menos uma cadeia de explicação:

evidência 1 + evidência 2
          ↓ regra
hipótese de diagnóstico
          ↓ regra
próxima verificação

5. Projete o sistema de inteligência

Agora pense na implementação. O programa deve manter separadas a base de conhecimento e o mecanismo de inferência.

Fatos observados
entrada do incidente
→
Mecanismo de inferência
procura regras aplicáveis
↔
Base de regras
conhecimento técnico

Construa em Python um sistema capaz de:

  • armazenar fatos observados;
  • armazenar regras com condições e conclusão;
  • identificar automaticamente regras aplicáveis;
  • adicionar novas conclusões aos fatos conhecidos;
  • repetir a inferência enquanto novas conclusões forem produzidas;
  • mostrar as conclusões e indicar qual regra produziu cada uma.
Não há código pronto nesta etapa. A ideia é usar a modelagem construída acima como especificação para o programa.

6. Teste um segundo incidente

Depois que o sistema funcionar, teste outro conjunto de fatos:

api_retorna_500
disco_cheio
cache_disponivel
banco_disponivel
conexoes_banco_normais

Sem alterar o mecanismo de inferência, quais conclusões deveriam mudar? Se o programa estiver bem separado, apenas os fatos de entrada precisam ser substituídos.

Ideia central da prática: o desafio principal não é escrever um if para cada situação, mas transformar conhecimento do domínio em uma base de regras que possa ser usada por um mecanismo de inferência genérico.

Limites

Quando as regras não bastam?

O mecanismo funciona muito bem quando o conhecimento pode ser escrito como regras claras. Problemas reais, porém, nem sempre se comportam dessa maneira.

Lacuna

Falta informação

falha_backend

banco_indisponivel ?

Não saber que o banco está indisponível não significa saber que ele está disponível.

Conflito

Duas regras discordam

R1 → ligar_ventilacao
R2 → nao_ligar_ventilacao

Se as duas forem aplicáveis, precisamos de algum critério para resolver o conflito.

Incerteza

Evidência não é certeza

SE febre E tosse
ENTÃO gripe ?

Febre e tosse podem aumentar a plausibilidade de gripe, mas não tornam a hipótese automaticamente verdadeira.

Ponte para a próxima etapa: quando “verdadeiro ou falso” é forte demais, precisamos representar graus de incerteza. É aí que entram probabilidade condicional e o Teorema de Bayes.

Síntese

Três ideias para levar da aula

  • Fatos descrevem aquilo que o sistema sabe sobre o caso.
  • Regras permitem derivar novos fatos por meio de inferência.
  • Regras determinísticas têm limites: lacunas, conflitos e incerteza exigem mecanismos adicionais.
