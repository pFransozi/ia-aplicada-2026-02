Representação

Como representar aquilo que o sistema sabe?

Representar conhecimento é colocar informações sobre um domínio em uma forma que o programa consiga armazenar e usar para raciocinar.

Fato

Algo conhecido no caso atual

api_retorna_500
banco_indisponivel

Relação

Conecta elementos do domínio

depende_de(api, banco)

Regra

Conhecimento que pode ser aplicado

SE api_retorna_500
ENTÃO existe_falha_backend
Ideia principal: fatos descrevem o caso. Regras descrevem conhecimento que pode ser aplicado ao caso. Uma conclusão é simplesmente um novo fato produzido pela aplicação de uma regra.

Regra embutida no código

if erro_500 and banco_indisponivel:
    causa = "banco"

Conhecimento explícito

SE erro_500 E banco_indisponivel
ENTÃO causa_banco

Em um sistema baseado em conhecimento, buscamos separar as regras do domínio do mecanismo que executa essas regras.

Inferência

Como o sistema produz uma conclusão?

O mecanismo de inferência verifica quais regras podem ser aplicadas aos fatos disponíveis. Cada conclusão produzida pode se tornar um novo fato e ativar outra regra.

Encadeamento para frente

Começamos com aquilo que sabemos e avançamos produzindo novas conclusões.

Fatos iniciais:
api_retorna_500
banco_indisponivel

R1: SE api_retorna_500
    ENTÃO existe_falha_backend

R2: SE existe_falha_backend E banco_indisponivel
    ENTÃO causa_provavel_banco

R3: SE causa_provavel_banco
    ENTÃO verificar_conexao_banco
api_retorna_500→R1 produz existe_falha_backend.
existe_falha_backend + banco_indisponivel→R2 produz causa_provavel_banco.
causa_provavel_banco→R3 produz verificar_conexao_banco.
Observe a cadeia: api_retorna_500 → existe_falha_backend → causa_provavel_banco → verificar_conexao_banco. Nem todos esses fatos existiam no início; parte deles foi derivada.

Só para reconhecer

E o encadeamento para trás?

Existe uma estratégia que começa pela hipótese que queremos verificar. Em vez de perguntar “o que posso concluir?”, perguntamos “o que preciso provar para sustentar esta conclusão?”.

EstratégiaComeça porPergunta
Para frenteFatos disponíveisO que posso concluir?
Para trásHipótese ou objetivoO que preciso provar?

Nesta aula, nosso foco será o encadeamento para frente.

Prática guiada

Diagnóstico de uma aplicação web

Vamos usar o mesmo problema para identificar fatos e regras, executar a inferência manualmente e depois observar como o mecanismo pode ser programado.

Fatos observados

F1: api_retorna_500
F2: banco_indisponivel
F3: servidor_tem_espaco

Regras disponíveis

R1: SE api_retorna_500
    ENTÃO existe_falha_backend

R2: SE existe_falha_backend
    E banco_indisponivel
    ENTÃO causa_provavel_banco

R3: SE existe_falha_backend
    E disco_cheio
    ENTÃO causa_provavel_disco

R4: SE causa_provavel_banco
    ENTÃO verificar_conexao_banco

1. Execute manualmente

  1. Comece apenas com F1, F2 e F3.
  2. Procure uma regra cujas condições já sejam verdadeiras.
  3. Adicione a conclusão dessa regra aos fatos conhecidos.
  4. Repita até nenhuma regra produzir informação nova.
  5. Registre a cadeia que justifica a conclusão final.

2. Compare com o mecanismo em Python

Os fatos e as regras já estão representados. O algoritmo abaixo precisa apenas verificar regras aplicáveis e adicionar novas conclusões.

fatos = {
    "api_retorna_500",
    "banco_indisponivel",
    "servidor_tem_espaco"
}

regras = [
    ({"api_retorna_500"}, "existe_falha_backend"),
    ({"existe_falha_backend", "banco_indisponivel"}, "causa_provavel_banco"),
    ({"existe_falha_backend", "disco_cheio"}, "causa_provavel_disco"),
    ({"causa_provavel_banco"}, "verificar_conexao_banco")
]

houve_mudanca = True

while houve_mudanca:
    houve_mudanca = False

    for condicoes, conclusao in regras:
        # issubset verifica se todas as condições da regra
        # já aparecem entre os fatos conhecidos.
        if condicoes.issubset(fatos) and conclusao not in fatos:
            fatos.add(conclusao)
            houve_mudanca = True

print(fatos)
O ponto da prática não é decorar esse código. É perceber que o mecanismo de inferência pode continuar igual enquanto trocamos os fatos e as regras do domínio.

Limites

Quando as regras não bastam?

O mecanismo funciona muito bem quando o conhecimento pode ser escrito como regras claras. Problemas reais, porém, nem sempre se comportam dessa maneira.

Lacuna

Falta informação

falha_backend

banco_indisponivel ?

Não saber que o banco está indisponível não significa saber que ele está disponível.

Conflito

Duas regras discordam

R1 → ligar_ventilacao
R2 → nao_ligar_ventilacao

Se as duas forem aplicáveis, precisamos de algum critério para resolver o conflito.

Incerteza

Evidência não é certeza

SE febre E tosse
ENTÃO gripe ?

Febre e tosse podem aumentar a plausibilidade de gripe, mas não tornam a hipótese automaticamente verdadeira.

Ponte para a próxima etapa: quando “verdadeiro ou falso” é forte demais, precisamos representar graus de incerteza. É aí que entram probabilidade condicional e o Teorema de Bayes.

Síntese

Três ideias para levar da aula

  • Fatos descrevem aquilo que o sistema sabe sobre o caso.
  • Regras permitem derivar novos fatos por meio de inferência.
  • Regras determinísticas têm limites: lacunas, conflitos e incerteza exigem mecanismos adicionais.
