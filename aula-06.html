A conexão continua existindo: uma inferência também pode ser vista como uma busca em um espaço de possíveis conclusões. A diferença está no significado do problema: em vez de buscar um caminho físico, buscamos o que decorre do conhecimento disponível.

Representação do conhecimento

O que o sistema sabe?

Representar conhecimento significa transformar informações sobre um domínio em uma forma que o programa consiga armazenar, consultar e usar para raciocinar.

Fato

Algo considerado verdadeiro no caso atual

api_retorna_500
banco_indisponivel

Relação

Conecta elementos do domínio

depende_de(api, banco)
executa_em(api, servidor_01)

Regra

Conhecimento geral sobre o domínio

SE api_retorna_500
E banco_indisponivel
ENTÃO causa_provavel_banco

Conclusão

Informação derivada

causa_provavel_banco
Ponto-chave: armazenar conhecimento não é a mesma coisa que inferir conhecimento. A base guarda o que sabemos; o mecanismo de inferência usa esse conteúdo para produzir novas conclusões.

Conhecimento declarativo × comportamento codificado

Abordagem procedural

if erro_500 and banco_indisponivel:
    causa = "banco"

A regra sobre o domínio está embutida diretamente no código de controle.

Abordagem baseada em conhecimento

FATOS
erro_500
banco_indisponivel

REGRA
SE erro_500 E banco_indisponivel
ENTÃO causa_banco

O conhecimento do domínio fica explícito e separado do mecanismo que aplica as regras.

Arquitetura

Base de conhecimento + mecanismo de inferência

Um sistema baseado em conhecimento separa o que sabe do processo usado para raciocinar sobre esse conhecimento.

Dados do caso
fatos observados
→
Mecanismo de inferência
aplica as regras
↔
Base de conhecimento
fatos gerais + regras

O resultado é uma conclusão que pode ser acompanhada por uma explicação: quais fatos foram usados e quais regras foram aplicadas?

Leitura da arquitetura

Considere a regra:

SE banco_indisponivel
E sistema_depende_do_banco
ENTÃO sistema_pode_falhar

Agora considere os dados do caso:

banco_indisponivel
api_depende_do_banco

Pergunta: o que pertence ao conhecimento geral do domínio e o que pertence apenas ao caso que estamos analisando?

Inferência

Produzindo novo conhecimento

Uma regra pode gerar uma informação nova. Essa nova informação pode ativar outra regra, criando uma cadeia de raciocínio.

Fatos:
A
B

Regras:
R1: SE A E B → C
R2: SE C → D
A + B→R1 é aplicável; concluímos C.
A + B + C→R2 passa a ser aplicável; concluímos D.
A + B + C + D→Não há nova regra aplicável; o processo pode parar.
Observe: C e D não foram informados como fatos iniciais. Eles foram derivados pelo sistema.

Estratégias de inferência

Para frente ou para trás?

Podemos raciocinar a partir dos fatos disponíveis ou começar por uma conclusão que desejamos verificar.

Encadeamento para frente: “o que posso concluir?”

Fatos:
erro_500
banco_indisponivel

R1: SE erro_500 → falha_backend
R2: SE falha_backend E banco_indisponivel → suspeita_banco
R3: SE suspeita_banco → verificar_conexao_banco

Passo 1: erro_500 permite aplicar R1 → falha_backend.

Passo 2: falha_backend + banco_indisponivel permitem aplicar R2 → suspeita_banco.

Passo 3: suspeita_banco permite aplicar R3 → verificar_conexao_banco.

Encadeamento para trás: “o que preciso provar?”

Suponha que a consulta seja:

suspeita_banco ?

Procuramos uma regra que conclua suspeita_banco:

SE falha_backend E banco_indisponivel
ENTÃO suspeita_banco

Agora a pergunta vira: falha_backend? e banco_indisponivel?. Para provar falha_backend, encontramos outra regra:

SE erro_500
ENTÃO falha_backend

Como erro_500 e banco_indisponivel são fatos, a consulta pode ser sustentada.

EstratégiaComeça porPergunta principal
Para frenteFatos disponíveisO que posso concluir?
Para trásObjetivo ou hipóteseO que preciso saber para provar isso?

Prática guiada

Diagnóstico de uma aplicação web

Vamos construir uma pequena base de conhecimento para investigar uma falha de software.

Fatos observados

F1: api_retorna_500
F2: banco_indisponivel
F3: servidor_tem_espaco

Regras disponíveis

R1:
SE api_retorna_500
ENTÃO existe_falha_backend

R2:
SE existe_falha_backend E banco_indisponivel
ENTÃO causa_provavel_banco

R3:
SE existe_falha_backend E disco_cheio
ENTÃO causa_provavel_disco

R4:
SE causa_provavel_banco
ENTÃO verificar_conexao_banco

Etapa 1 — Identifique a estrutura

  1. Quais elementos são fatos?
  2. Quais elementos são regras?
  3. Em cada regra, o que é condição e o que é conclusão?
  4. Qual informação ainda não está nos fatos, mas pode ser derivada?

Etapa 2 — Execute manualmente

Comece apenas com F1, F2 e F3. Aplique as regras possíveis e registre cada novo fato produzido. Pare quando nenhuma nova informação puder ser adicionada.

Etapa 3 — Explique a conclusão

Se o sistema concluir verificar_conexao_banco, produza a cadeia de justificativa mostrando os fatos e regras utilizados.

Transforme a ideia em Python

A estrutura abaixo já representa os fatos e as regras. Complete apenas o núcleo do mecanismo de inferência.

fatos = {
    "api_retorna_500",
    "banco_indisponivel",
    "servidor_tem_espaco"
}

regras = [
    ({"api_retorna_500"}, "existe_falha_backend"),
    ({"existe_falha_backend", "banco_indisponivel"}, "causa_provavel_banco"),
    ({"existe_falha_backend", "disco_cheio"}, "causa_provavel_disco"),
    ({"causa_provavel_banco"}, "verificar_conexao_banco")
]

houve_mudanca = True

while houve_mudanca:
    houve_mudanca = False

    # 1. percorra as regras
    # 2. verifique se todas as condições estão em fatos
    # 3. se a conclusão ainda não existir, adicione-a
    # 4. marque que houve mudança

print(fatos)
Objetivo da prática: perceber que o algoritmo de inferência pode permanecer genérico enquanto o conhecimento do domínio é alterado pela inclusão, remoção ou modificação de regras.

Limites

Regras não resolvem tudo

Sistemas baseados em conhecimento são úteis porque tornam o raciocínio explícito, mas dependem diretamente da qualidade e da completude das regras representadas.

Conflito

Duas regras recomendam ações incompatíveis

SE temperatura_alta
ENTÃO ligar_ventilacao

SE sensor_manutencao
ENTÃO nao_ligar_ventilacao

Se as duas condições forem verdadeiras, precisamos decidir qual regra tem prioridade.

Lacuna

Não saber não significa saber o contrário

SE falha_backend E banco_indisponivel
ENTÃO causa_banco

Se sabemos apenas falha_backend, não podemos concluir que o banco está disponível nem indisponível.

O limite que leva à próxima aula

Considere a regra:

SE febre E tosse
ENTÃO gripe

Ela é muito forte: febre e tosse não tornam a hipótese “gripe” automaticamente verdadeira. Em muitos problemas reais, uma evidência apenas torna uma hipótese mais ou menos provável.

Próxima etapa: quando fatos e regras determinísticos não são suficientes, precisamos representar incerteza. Na próxima aula, vamos usar probabilidade condicional e o Teorema de Bayes para atualizar crenças a partir de evidências.
